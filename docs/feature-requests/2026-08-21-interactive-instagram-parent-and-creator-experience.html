Interactive Instagram parent and creator experience

Turn Tiny SOHO’s comment-to-DM automation from a text gate followed by a file sequence into a coherent, measurable parent journey—and give the creator one visual workspace to build, preview, publish and improve that journey safely.

Executive summary

This feature request treats the parent’s Instagram conversation and the creator’s console as two views of one product. A parent should see a native, low-friction, useful conversation. The creator should see the exact same journey as a versioned visual flow, not reconstruct it mentally across Content, Keywords and Sequences.

Recommended first release Validate whether a native one-tap response is supported on the initial comment private-reply path, then run one end-to-end experiment for one high-volume keyword. The slice includes the parent interaction, the creator’s complete preview, explicit draft/save/publish states, launch validation and durable measurement. It does not attempt the entire roadmap at once.
Instagram post→ Keyword comment→ Public reply→ Opening DM→ Parent action→ Guide→ Next value→ Measured outcome

Why both sides belong together

  • A new parent-facing interaction cannot ship safely unless the creator can configure and preview it.
  • A beautiful creator editor is not valuable if production can still send only the old text-only path.
  • The preview, sender, action router and measurement system should consume the same versioned journey definition.
  • Every visual enhancement must correspond to an actual Meta-supported payload and a measurable event.

Problem evidence and current state

Largest parent loss: answering the gate

Historical 30-day evidence in the canonical backlog records 1,588 opened conversations, 1,565 delivered gate DMs and 622 user replies—approximately 40%. About 943 people received the gate wording but never replied. Everything downstream performed comparatively well.

Repeat value is rare

Of 1,266 people who completed a keyword flow, 1,203 completed exactly one and only 63 completed two or more. The current repeat-interaction baseline is therefore about 5%.

Returning relationships already exist

2,369 current followers had completed at least one guide; 284 later requested a different resource. The system has enough returning behavior to justify respectful recognition without exposing private history.

The creator enters for setup, not analysis

The product record says the creator posts a Reel or carousel, logs in, attaches keywords and edits sequences. Analytics exist for decisions she owns, but the daily setup surfaces do not carry the relevant finding back into that workflow.

Platform capabilities and constraints

  • Quick replies provide native preset responses. Meta documents a maximum of 13 text choices, each limited to 20 characters; they are not available on desktop Instagram.
  • Button templates support up to three postback or URL actions.
  • Generic templates can combine images, text and buttons; multiple elements form a horizontal carousel.
  • Ice breakers support up to four starter questions and are mobile-only.
  • The initial comment private reply is one message. Meta’s documented sample uses text. Follow-up messages become possible only after the recipient responds and must respect the current messaging window.
  • Instagram controls the native appearance. Tiny SOHO controls content, sequence, imagery, actions, branching and timing—not button color, typography or layout.
  • The screenshot that inspired this request demonstrates a one-tap pattern, but the exact initial-private-reply payload must be verified with Tiny SOHO’s login type, permissions and current API version before the design treats it as guaranteed.

Product constraints this request preserves

  • Two console users continue to share one permission model. No role-specific console is introduced.
  • Template automation may send only after a person configures and publishes it. AI-authored copy remains owner-reviewed.
  • Guide access is not conditional on following, sharing, answering an optional profile question or continuing a conversation.
  • Public messages never reveal facts learned privately.
  • Ambiguous provider outcomes are never retried automatically when doing so could duplicate a real message.
  • The console interprets evidence only when the sample supports the claim; otherwise it presents qualified counts.

Parent Instagram experience

The desired parent experience is warm, concise and native to Instagram. It reduces effort before value, makes the delivered resource feel intentional, and offers a useful next step without turning the conversation into a growth trap.

1

One-tap guide unlock

Replace manual DONE typing with a clearly labeled native response when the private-reply capability spike confirms support. The button must generate a normal inbound message event and open the valid follow-up window. Any free-text response must continue to work.

2

Known-follower path

When cached follower state is confidently true, use warm recognition instead of asking the person to follow again. Unknown status uses neutral wording, not a claim. Recognition changes copy only; it does not expose history or gate the guide.

3

Visually packaged guide

Deliver a short introduction, useful image/card, concise instructions and the downloadable resource in a deliberate order. Every image includes reviewed alternative text, and the delivery remains usable when rich templates are unavailable.

4

Choose the next need

After the requested guide has been delivered, offer a small set of relevant topics such as sleep, meals or activities. This is a post-value choice, not a prerequisite. Record the selected need as an explicit answer.

5

Optional age-aware recommendations

Explain why an age band would improve suggestions, provide a Skip action and ask only after value. Start by measuring answer viability; do not build automated routing until parsing, privacy and content coverage pass their thresholds.

6

Returning-parent recognition

Acknowledge that the person is returning and deliver the newly requested resource. Private history may prevent repetition behind the scenes, but no private fact is copied into a public comment or unnecessary DM.

7

Saveable parenting artifact

Offer one reviewed static bedtime card, routine checklist, recipe card or activity card. Saving and downloading work without social sharing, names or exact child age. Tiny SOHO attribution remains subtle.

8

Lightweight feedback

After value and only inside a valid window, ask whether the resource helped using two low-effort responses. Negative or nuanced feedback opens a human-review path rather than an automated persuasion sequence.

9

Inbox ice breakers

Provide up to four stable starter questions for visitors who begin from the profile inbox: sleep guides, toddler recipes, activities and a general parenting question. Each route has a safe deterministic first response or human handoff.

10

Persistent resource menu

Provide a small account-wide menu for browsing guides, reopening the latest resource or asking Tiny SOHO. The menu is not personalized with sensitive data and never promises a human reply that cannot be delivered.

Parent copy principles

  • Lead with the requested value; do not make parents prove loyalty.
  • Use warm, practical, concise language and at most one contextually appropriate emoji.
  • Never diagnose, shame, pressure, invent personal familiarity or imply that an unreviewed AI message was personally typed.
  • Every optional question explains its purpose and includes a skip path.
  • Buttons use explicit verbs: “Send me the guide”, “Open full guide”, “Skip for now”. Avoid vague “Yes” or “Continue”.
  • The typed-message fallback remains supported for accessibility, desktop Instagram and unsupported clients.

Creator console experience

The creator console should organize itself around the daily job: connect the new post, verify the entire audience journey, publish safely and return later to understand whether it worked. Existing account-wide inventory remains available without forcing daily setup through separate pages.

1

Daily publishing workspace

Show new and upcoming posts with clear states: needs setup, draft, ready, live or needs attention. Rank the one next setup action. Upcoming automations remain visible before a post is published and become bindable afterward.

2

Post automation studio

Represent the full journey on one page: post, keyword, public reply, opening DM, parent action, guide and closing action. Selecting a step opens a focused editor. Keywords and Sequences remain account-wide inventory surfaces until the studio truly absorbs their full jobs.

3

End-to-end Instagram preview

Render the complete experience, not only the post-DONE sequence. Switch among new parent, known follower and returning parent. Preview mobile-native limitations and a desktop/text fallback. The preview consumes the same versioned definition as production.

4

Interactive block library

Add typed blocks for text, image, PDF, quick replies, button templates and carousel cards. Unsupported combinations fail validation. Every action has a stable payload, explicit destination and fallback behavior.

5

Launch-readiness checklist

Validate the connected post, trigger uniqueness, message limits, media/link availability, complete branch destinations, follower wording, alternative text and measurement readiness before publication.

6

Explicit save and live versions

Authored text remains a local draft until Save changes or the documented keyboard shortcut. Structural operations may remain immediate. Saving and publishing are separate. Navigation warns while dirty or saving, and failed saves preserve the draft.

7

Results attached to the post

Bring the post’s measured journey back into the setup surface: keyword requests, opening replies, parent responses, guides delivered and qualified follow evidence. State the largest eligible loss and one evidence-backed next move.

8

Safe A/B experiments

Version exact copy and block definitions, assign participants deterministically, declare the primary outcome and threshold before launch, and preserve the exact experience each person received. Prevent overlapping experiments that confound the same cohort.

9

One actionable people queue

Show one row per person only when a human decision is required. Consolidate reasons into badges and open the complete corrected timeline. This feature waits for REL-001 and real draft examples rather than inventing another partial history.

10

Mobile quick-edit mode

Keep mobile narrow: choose the newest post, attach a validated automation, verify the active trigger and leave. Experiments, bulk changes and deep analysis remain desktop work.

Creator information architecture

  • Content becomes the daily post-centric entrypoint and may host the Automation Studio.
  • Keywords remains the account-wide trigger inventory for editing, pausing and deleting until every one of those jobs is safely absorbed elsewhere.
  • Sequences remains the reusable guide library and detailed block editor.
  • Home keeps cross-product interpretation and the single ranked next move.
  • Conversations evolves toward one actionable queue and complete person view only after its lineage is correct.

Shared experience architecture

The recommended architecture introduces a versioned interactive journey rather than adding one-off button fields to Keyword and Resource. The unit must be understandable by the authoring UI, preview renderer, sender, action router and analytics without each subsystem inventing a parallel interpretation.

Conceptual data contracts

  • Journey: stable identity, media/post association, lifecycle state, current draft and published version.
  • JourneyVersion: immutable version number, content snapshot, policy version, creator, timestamps and optional experiment arm.
  • JourneyBlock: stable block ID, type, ordered content, accessibility metadata and delivery fallback.
  • JourneyAction: stable payload ID, visible label, action type, destination block or URL, eligibility and expiry behavior.
  • JourneyExecution: one participant/post-trigger run with resolved version, audience state and window state.
  • JourneyEvent: append-only observation for exposure, provider acceptance, inbound choice, transition, failure, uncertainty, completion and suppression.
  • ParentProfileFact: separately governed explicit answer with purpose, provenance, confidence, correction/deletion state and retention policy. It is not general assistant memory.

State and transition requirements

  • Every action payload names the journey version, action and execution using an opaque signed or server-resolved identifier; never trust client-readable labels for routing.
  • Webhook handling is idempotent by provider message/postback identity. A repeated webhook cannot deliver the next block twice.
  • A free-text reply while a quick-reply prompt is open follows a defined fallback: continue the guide for an unlock prompt, or route to existing conversation handling for substantive text.
  • A newer journey from the same person cannot accidentally satisfy an older open action without an explicit compatibility rule.
  • Closed messaging windows, deleted posts, unavailable media, invalid URLs and provider uncertainty become visible execution states.
  • Publishing validates the complete reachable graph. No visible action may point to a missing, draft-only or unsupported destination.

Save and publish model

  1. Editing produces local dirty state.
  2. Save changes persists a draft snapshot and preserves newer typing that occurred while the request was in flight.
  3. Publish promotes a validated immutable version. Existing executions remain pinned to the version they entered unless an explicit migration is approved.
  4. Pausing prevents new executions but does not erase evidence or silently cancel deliveries already in progress.
  5. Rollback republishes a known valid historical version as a new auditable release; it does not mutate history.

Policy, privacy and safety

Guide access and growth

  • Deliver the requested resource after the person opens the messaging path.
  • Do not condition access on following, sharing, feedback or profile answers.
  • Test follow asks separately with control, treatment and stable evidence.

Parent data

  • Collect only explicit facts tied to a defined recommendation purpose.
  • Provide Skip, correction and deletion behavior.
  • Never expose exact age in public or shareable output by default.

Public versus private context

  • Public copy may acknowledge a relationship in general terms.
  • Private facts never enter a public prompt or automatic comment.
  • Context-aware public drafting remains owner-reviewed in its first slice.

Human authority

  • Deterministic published templates may run unattended.
  • AI drafts require review under the current product boundary.
  • Sensitive, medical, developmental, hostile or ambiguous content hands off.

Measurement and experiment contract

Recommended first-slice hypothesis

A shorter opening DM with one native one-tap response produces a higher matching guide-completion rate than the current typed-reply gate, without increasing complaints, opt-outs, delivery ambiguity or duplicate sends.

Experiment rules

  • Resolve assignment deterministically from a stable participant identifier plus experiment namespace.
  • Store the exact visible copy, block definition, payload mapping, journey version, keyword, post and timestamps.
  • Define eligibility, exclusions, attribution window, minimum sample and minimum useful lift before launch.
  • Do not overwrite mutable Keyword copy and reconstruct history from its latest value.
  • Do not launch overlapping public-copy, recovery and opening-DM experiments on the same cohort unless the analysis can isolate them.
  • Do not declare a winner early or select whichever metric happens to look best.

Recommended staged rollout

0

Capability and correctness gate

Verify Meta payloads against the current API version and app permissions, especially quick replies on the initial private reply. Resolve guide/follow policy, complete the required audit trail, define block limits and instrument provider evidence. Integrate or deliberately supersede the focused REL-006 save work.

1

One vertical experiment

Choose one revalidated high-volume keyword. Ship the shortest complete path: versioned opening copy, one-tap action or documented fallback, exact creator preview, explicit saves, launch checks, action routing and outcome evidence. Keep the guide content otherwise unchanged.

2

Post automation studio

Move the post’s complete journey into a single authoring surface, add supported block types and attach qualified results to the post. Preserve inventory pages until no unique job is lost.

3

Post-value retention

Test one optional next-need prompt. Separately run PARENT-001 answer-rate and conservative parsing slices before age-aware automated routing. Do not bundle a channel invitation into the same learning period.

4

Returning value and artifacts

Add returning-parent recognition and one static saveable artifact for a measured high-volume need. Keep sharing optional and avoid exact-age personalization until profile rules are proven.

5

Discovery and human workflow

Add ice breakers and the persistent menu after their deterministic destinations exist. Build the unified Needs You queue only after REL-001 and real shadow/approved draft evidence provide trustworthy rows.

Release controls

  • Every new block type and action router ships behind an explicit server-side enablement boundary.
  • Roll out by journey/version allowlist before percentage rollout.
  • Keep the existing text path available as a kill-switch fallback.
  • Document live owner, deployment steps, observation window and rollback trigger.
  • Do not migrate active production traffic merely because a draft was saved.

Acceptance criteria

Parent experience

  • An eligible comment receives exactly one allowed private reply and records the provider outcome.
  • If the initial one-tap action is supported, tapping it creates one idempotent inbound/action event and advances the correct published journey version.
  • Free-text responses still unlock the requested guide; DONE is an analytics hint, not a brittle parser requirement.
  • Known followers never receive factually incorrect “follow first” wording.
  • Unknown follower status never produces a false familiarity claim.
  • The guide remains available without following, answering optional questions, giving positive feedback or sharing.
  • Next-need and age prompts appear only after requested value and include Skip where personal data is involved.
  • Unsupported desktop/native controls have a usable text fallback.
  • Every sent block has durable success, retryable failure, terminal failure or uncertain evidence; uncertain sends are not automatically retried.

Creator experience

  • One post workspace shows every reachable step from comment through terminal outcome.
  • The preview renders new, known-follower, returning and unsupported-client paths from the same saved journey version as production.
  • The editor cannot publish unsupported block combinations, missing action targets, excessive button counts, overlong labels/messages, inaccessible images or broken required URLs.
  • Draft, dirty, saving, saved, publishing, live, failed and needs-attention states are explicit.
  • Saving does not silently publish; publishing creates an immutable auditable version.
  • Failed and partial saves preserve local work and do not misreport “All changes saved”.
  • Leaving while dirty or saving produces the approved navigation warning.
  • Post results state evidence windows, denominators, qualifications and missing coverage.
  • Experiments preserve exact variants and prevent ambiguous cohort overlap.
  • Mobile quick edit exposes only validated post binding, trigger and activation—not destructive bulk operations.

Accessibility and responsive behavior

  • All console controls are keyboard accessible with visible focus and screen-reader labels.
  • Meaning never depends on color alone; states include text and icons.
  • Phone preview is not the only representation of message content.
  • The studio remains usable at the existing supported desktop widths and reduces to the explicit mobile quick-edit flow on narrow screens.
  • Alternative text is required for authored informational images and retained in the published version.

Decisions required before implementation slices

  1. First-release outcome: approve matching guide completion as the primary first-slice outcome, with opening response as the mechanism metric.
  2. Private-reply capability: accept the capability-spike result as the authority for whether the one-tap control can appear in the initial DM.
  3. Follow treatment: confirm that follow asks may be tested but never block the requested guide.
  4. First keyword: revalidate current traffic before selecting the first experimental keyword; historical volume alone is not sufficient.
  5. V1 block types: recommended first set is text, image, PDF and quick replies; button templates and carousels follow after the core compiler/router is proven.
  6. Save/publish model: approve separate explicit Save and Publish actions rather than implicit live mutation.
  7. Age-loop form: measure one optional question first; select exact age versus age band only after copy/privacy review. The mock’s age bands are a concept, not a settled product decision.
  8. Creator results: approve which post-level outcomes can be measured honestly with current Meta coverage.
  9. Admin cadence: decide whether the Needs You queue is checked more than once daily or mainly each morning; this determines its default sort.
  10. Navigation absorption: do not remove Keywords or Sequences until a focused design proves that the studio covers their account-wide jobs.

Explicitly out of scope for the first release

  • Broad autonomous AI conversations or AI-controlled sending policy.
  • Medical, developmental or psychological advice.
  • Automated affiliate/product recommendation.
  • A full personalized resource catalog before repeat demand and content coverage are measured.
  • Exact child-age exposure in public or shareable artifacts.
  • Mandatory sharing, advocacy or channel joining.
  • Wholesale navigation redesign or role-based permissions.
  • Merging divergent feature branches wholesale.

Definition of done for this feature request

This document is a product proposal and visual specification, not implementation authorization. The feature is complete only when:

  • The capability and policy decisions above are recorded.
  • The selected vertical slice has a focused technical design and implementation plan.
  • The live creator UI and Instagram delivery compile from the same versioned journey.
  • The first experiment reaches its predefined sample or stop rule with auditable evidence.
  • The creator can build, preview, validate, save and publish without ambiguous live state.
  • A parent can request and receive the guide without unnecessary friction or coercive requirements.
  • Operations can identify, pause and roll back the exact journey version safely.
  • The canonical backlog is updated with the resulting decision, implementation links and shipped state rather than duplicating scope indefinitely.
